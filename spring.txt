# Task: Add a Complete Spring Framework Learning Section to JavaTrail

## Objective

Add a new top-level navigation menu named **Spring Framework** to the existing JavaTrail website.

The website follows a W3Schools-style tutorial experience. The new section must provide a structured, beginner-to-advanced learning path for the **Spring Framework itself, not Spring Boot**.

The goal is not merely to create a navigation menu. Build the complete curriculum structure, create meaningful lesson content for every topic and subtopic, and integrate it with the existing tutorial rendering and navigation system.

## 4. Lesson content quality requirements

Do not create empty pages or pages containing only a title and a short definition.

Every lesson must teach the concept thoroughly, using a consistent W3Schools-style tutorial format.

Each lesson should include:

1. **What is it?** Explain the concept in simple English.
2. **Why do we need it?** Explain the problem it solves.
3. **How does it work?** Explain the lifecycle, internal process, or execution flow.
4. **How to configure it?** Show the relevant XML, Java configuration, or annotations.
5. **Complete runnable example.** Include imports, required classes, configuration, and an entry point where appropriate.
6. **Expected output.** Show actual output and explain why it occurs.
7. **Step-by-step execution.** Explain what happens when the code runs.
8. **Real-world scenario.** Use realistic examples such as employee management, orders, payments, logging, or database access.
9. **Common mistakes.** Explain errors, incorrect assumptions, and debugging techniques.
10. **Interview questions.** Include practical questions appropriate for experienced Java developers.
11. **Practice exercise.** Include a problem, expected behavior, and solution or revealable answer.
12. **Related concepts.** Link to relevant lessons in the Spring Framework section.

Adapt the structure to the subject. For example, an architecture lesson needs a diagram; an annotation reference needs usage examples; a transaction lesson needs commit, rollback, and propagation scenarios.

Use diagrams when they clarify relationships, object lifecycles, execution sequences, or request flows. Avoid decorative diagrams that do not teach anything.

Explain advanced terminology when it first appears. Do not assume the learner already understands the internal behavior of Spring.

## 5. Runnable examples

The current site uses a local Java compiler/runner through `/api/run`.

Do not assume Spring Framework code can run in the existing plain-Java runner.

For Spring examples:

- Clearly distinguish standalone Java examples from Spring application examples.
- Provide complete source files and the required Maven or Gradle dependencies.
- Include the necessary Spring configuration and application entry point.
- Explain how to run the example in a real Spring project.
- If the existing editor cannot execute the example, display the code and instructions without falsely claiming it ran.
- Never add Spring dependencies to the existing Java runner unless the existing architecture explicitly supports a safe and maintainable extension.
- Keep the current Java Try It functionality working.

Where practical, provide examples that use an in-memory or mock implementation before introducing a database or external service.

## 6. Spring Framework, not Spring Boot

This is a strict requirement.

Do not create Spring Boot as the main curriculum or use it as a shortcut for configuring Spring Framework.

Avoid:

- @SpringBootApplication
- SpringApplication.run()
- Spring Boot starters as the default dependency mechanism
- Spring Boot auto-configuration as a substitute for understanding Spring configuration
- application.properties examples that depend on Spring Boot-specific behavior
- Spring Boot CLI or Actuator as core requirements

Instead, teach explicit configuration with the Spring Framework itself.

For example, teach:

- AnnotationConfigApplicationContext for standalone annotation-based applications.
- ClassPathXmlApplicationContext for XML-based applications.
- Explicit Maven or Gradle dependencies.
- Explicit DataSource and transaction manager configuration.
- DispatcherServlet and WebApplicationInitializer or equivalent servlet-container configuration for web applications.
- Standard Spring testing APIs.

If a comparison with Spring Boot is useful, explain the difference briefly, but do not turn it into a Spring Boot tutorial.

## 7. Version and compatibility requirements

Before implementing lessons, determine a consistent supported Spring Framework baseline.

- Inspect the project's JDK version and current Java examples.
- Prefer a stable Spring Framework version compatible with the project's supported JDK.
- Document the chosen Spring Framework and Java versions.
- Distinguish APIs that differ between Spring Framework 5, 6, and 7.
- Account for the `javax.*` to `jakarta.*` transition in Spring Framework 6.
- Identify features that are version-specific or deprecated.
- Do not present removed APIs as current best practices.
- Verify version-sensitive details against official Spring documentation.

Do not mix incompatible dependencies or configuration styles in a single runnable example.
